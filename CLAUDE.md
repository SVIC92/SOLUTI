# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"SoluTI_AI" — a Help Desk / IT ticketing system with AI-assisted triage, chatbot, copilot and
anomaly detection. It's a polyglot monorepo with three independently-run apps that share one
Postgres database:

```
backend/             NestJS + Prisma — the core: auth, tickets, notifications, reports,
                      SLA, CMDB, KB, automation/routing, CSAT surveys, multi-channel gateway.
frontend/             Angular 19 SPA (standalone components, no NgModules).
services/ai-service/  Python/FastAPI microservice — triage, chatbot, copilot, anomaly
                       detection, KB draft generation. Talks to `backend` over HTTP and Redis.
docker-compose.yml    On-premise orchestration (backend + ai-service + its 4 workers + redis
                       + frontend). Neon Postgres is external to this compose file.
```

Original functional spec lives in `1.txt` (core Help Desk modules) and `2.txt` (AI modules) at
the repo root — module docstrings/comments across the codebase reference these as "el plan".
`README.md` tracks which phases/modules are actually implemented; `DEPLOYMENT.md` covers the
Vercel (frontend) / Render (backend) production setup and the still-undecided ai-service host.

## Commands

### backend/ (NestJS, ESM, Node >=22 <23)

```bash
npm run start:dev        # watch mode, http://localhost:3000/api/v1, Swagger at /api/docs
npm run build             # nest build
npm run lint              # oxlint src/ test/ (NOT eslint)
npm test                  # vitest run (unit specs, *.spec.ts next to the code)
npx vitest run path/to/x.spec.ts   # single test file
npm run test:e2e          # vitest run --config ./vitest.config.e2e.ts (test/*.e2e-spec.ts)
npx prisma migrate dev --name <desc>   # after editing prisma/schema.prisma
npm run db:seed           # seeds roles + default admin (see Auth section below)
```

Note: `prisma/migrations/` is not currently checked into the repo (no migration history), so
the Neon DB's actual schema may have drifted from what `prisma migrate dev` expects. If it
complains about drift, that's expected — reconcile with `prisma migrate resolve` rather than
assuming the schema file is wrong.

### frontend/ (Angular 19, standalone components)

```bash
npm start                 # ng serve, http://localhost:4200
npm run build              # ng build
npm test                   # ng test (Karma/Jasmine, runs in a real Chrome instance)
```

No dedicated single-test CLI flag; use Jasmine's `fdescribe`/`fit` to isolate a spec while
running `ng test`.

### services/ai-service/ (Python 3.13, FastAPI)

```bash
python -m venv .venv && .venv/Scripts/activate   # Windows; source .venv/bin/activate elsewhere
pip install -r requirements.txt -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
python -m app.workers.triage_worker        # + embedding_worker / anomaly_scheduler / kb_generator_worker
pytest                                      # tests/ (pytest + pytest-asyncio)
pytest tests/test_security.py::test_name    # single test
psql "$DATABASE_URL" -f migrations/001_pgvector_and_ai_tables.sql   # one-time, pgvector + ai_* tables
```

## Architecture

### Data ownership split

One Neon Postgres instance, two schema owners: `backend`'s `prisma/schema.prisma` owns the
core tables (users, tickets, comments, assets, KB articles, SLA policies, etc.), migrated with
Prisma. `ai-service` owns the `ai_*` tables (analysis, embeddings, chatbot sessions, anomaly
clusters), migrated with Alembic/raw SQL (`migrations/001_pgvector_and_ai_tables.sql`) —
independent from Prisma's migration history. `ai-service` reads core tables directly with raw
SQL/SQLAlchemy; it never goes through Prisma.

**Gotcha:** Prisma's `id String @id @default(uuid())` columns are stored as `TEXT`, not the
Postgres `uuid` type, even though the values look like UUIDs. Raw SQL in `ai-service` must
never `CAST` a core-table id to `::uuid` — it will fail or silently misbehave against `TEXT`
columns.

### Backend (`backend/`)

- Prisma 7's `prisma-client` generator (see `prisma/schema.prisma`'s `generator client` block,
  output `src/generated/prisma/`, gitignored, regenerated by `postinstall`/`prisma generate`).
  It no longer accepts an implicit `DATABASE_URL` — `PrismaService` (`src/database/prisma.service.ts`)
  wires it explicitly via `@prisma/adapter-pg`'s `PrismaPg`. There is deliberately no `url` line
  in the `datasource` block.
- Global prefix `api/v1`, global `ValidationPipe({ whitelist: true, transform: true,
  forbidNonWhitelisted: true })`, Swagger at `/api/docs` — all wired in `src/main.ts`. Every DTO
  needs `class-validator` decorators or requests get silently stripped/rejected.
  `Joi`-based env validation (`src/config/validation.schema.ts`) fails fast at boot if a
  required var (`DATABASE_URL`, JWT secrets, `SMTP_HOST`, `AI_SERVICE_API_KEY`, ...) is missing;
  most channel-specific vars (LDAP, WhatsApp, Slack, Teams) are optional and each integration
  degrades to a 503 rather than crashing the app when unconfigured.
- **Auth**: JWT access (15m) + refresh (7d) tokens, both carrying only `{ sub, email, role,
  groupId }` (`AuthService.issueTokens`). `RolesGuard` (`src/common/guards/roles.guard.ts`)
  allows any authenticated user through when a handler has no `@Roles(...)` — only routes that
  explicitly declare roles are restricted. LDAP/AD SSO (`POST /auth/login/ldap`) provisions a
  local `User` row on first login via `ExternalIdentityService`; `authProvider` on `User`
  distinguishes LOCAL/LDAP/AD/SERVICE/WHATSAPP/SLACK/TEAMS accounts (self-service password
  change is only ever allowed for LOCAL).
- **Nest routing gotcha**: static path segments must be declared before `:param` routes at the
  same level, e.g. `UsersController`'s `@Get('me')` is declared before `@Get(':id')` — otherwise
  Nest/Express matches `/users/me` against `:id` first.
- **Domain events → ai-service bridge**: business logic emits in-process events via
  `@nestjs/event-emitter` (see `src/common/events/event-types.ts` for the full `DomainEvent`
  registry and payload shapes). `AiEventPublisher` (`modules/ai-gateway/event-publisher.ts`)
  listens to all of them and republishes to the `core-events` Redis Stream for `ai-service` to
  consume asynchronously — if Redis is down, it logs and swallows the error (the core must keep
  working without AI features, "degraded mode"). The reverse direction — `ai-service` writing
  triage/classification results, chatbot-initiated tickets, or anomaly alerts back into the core
  — goes through `modules/ai-gateway/ai-internal.controller.ts`, guarded by
  `ServiceApiKeyGuard` (shared `AI_SERVICE_API_KEY` secret, constant-time comparison) instead of
  user JWTs.
- **Users module** (`modules/users/`) deliberately has no hard-delete: users have tickets,
  comments, attachments, etc. attached, so admin management only supports deactivating
  (`isActive`) plus reassigning role/group. Self-service (`GET/PATCH /users/me`, password
  change) is separate from admin management (`PATCH /users/:id`, admin-only); an admin cannot
  deactivate or demote their own account through the admin endpoint (see the guard in
  `UsersController.update`).

### Frontend (`frontend/`)

- Every component is standalone (`standalone: true`, explicit `imports: [...]`); there are no
  NgModules besides what Angular CLI needs internally. Routes are lazy-loaded per feature via
  `loadComponent` in `src/app/app.routes.ts`.
- Route guards: `authGuard` (`core/auth/auth.guard.ts`) only checks "is there a valid,
  unexpired JWT" and redirects to `/auth/login`. `roleGuard(['ADMIN', ...])` (a guard
  *factory*, `core/auth/role.guard.ts`) additionally checks the decoded role and redirects to
  `/dashboard` on mismatch — apply both together when a route is role-restricted, and keep the
  sidebar's `NavItem.roles` in `layout/main-layout.component.ts` in sync (it's a UX nicety only;
  the router guard is the real enforcement).
- `AuthService.currentUser` is **not** a signal — it's a getter that decodes the JWT payload on
  every access (`TokenService.getCurrentUser()`), so it only ever exposes `sub`/`email`/`role`/
  `groupId`. There is no client-side refresh-token flow: `jwt.interceptor.ts` attaches the
  access token to every request, and `error.interceptor.ts` just clears the session and
  redirects to login on any 401 — the stored refresh token is currently unused. Anything beyond
  those four JWT fields (e.g. `fullName`, `createdAt`) requires a real HTTP call to
  `GET /users/me` (see `features/profile/`).
- Feature folders under `features/*` each own their `.component.ts`/`.html` and usually a
  sibling `*.service.ts` (thin `HttpClient` wrapper, one method per endpoint, `providedIn:
  'root'`) — see `features/tickets/ticket.service.ts` or `features/users/user.service.ts` as
  the canonical shape to copy for a new feature.
- Design system ("SoluTI_AI", exported from Stitch): Tailwind with a fully custom token set in
  `frontend/tailwind.config.js` — flat color names (`surface-card`, `on-surface-variant`,
  `primary-container`, `status-resolved`, `ai-purple`, ...), custom `space-*` spacing scale, and
  every `font-*` family token mapped to `"JetBrains Mono"` (the whole app is intentionally
  monospaced). There is no modal/dialog component anywhere in the app — destructive or
  create/edit flows use an inline expandable form panel instead (see
  `features/users/user-management.component.html` or `features/tickets/ticket-create/`).

### ai-service (`services/ai-service/`)

FastAPI app (`app.main:app`) plus four standalone worker processes
(`app/workers/{triage,embedding_worker,anomaly_scheduler,kb_generator_worker}.py`) that each
run their own `asyncio` loop consuming the `core-events` Redis Stream — modeled as separate
`docker-compose.yml` services today. Each process that touches embeddings
(`app/core/embeddings.py`, `BAAI/bge-m3` via `sentence-transformers`) loads its own ~1-2GB copy
of the model via `@lru_cache`, since the cache is per-process — `DEPLOYMENT.md` section 3 has
the full cost/architecture analysis and the (not-yet-built) plan to fuse all 5 processes into
one to share that cache. Classification/generation calls Gemini (`google-genai`); routing
decisions (which technician gets a ticket) are plain DB queries, no LLM involved.
